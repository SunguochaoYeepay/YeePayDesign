# 原型生产体系演进路线图

## 目标

将“业务自然语言 -> 受控 Page Spec -> Vue/Ant 预览”稳定为可复用的生产能力，而不把
项目演变成 AI 随机拼页面的工具箱。

```text
业务需求 -> Page Spec -> 固定渲染器 -> 人工验收 -> 回归样例 -> 新能力准入
```

## 阶段 A：视觉基线冻结

**优先级最高。** 先把现有 `form`、`list`、`detail` 与 `result` 的视觉语言定准，再扩展组件。

工作项：

1. UI 审核十七个 Vue/Ant POC，给出 Token、间距、字号、表单标签宽度、表格密度、
   按钮、空状态和插图占位的明确规范。
2. 将结论沉淀到 `tokens.css`、Vue/Ant theme 配置和
   `design-system/vue-ant/page-runtime.css`，不写进业务提示词。
3. 选定 1280px 和常用窄屏后台宽度作为人工验收视口。
4. 冻结十七个 POC 的 Page Spec 与预览为第一批视觉回归样例。

通过门槛：同一份 Page Spec 连续构建不漂移；用户只需修改业务内容，不需重复纠正
控件基础样式或交互。

## 阶段 B：组件语义扩展

每次只开放一个真实业务需要的能力。流程固定为：真实需求 -> Page Spec 扩展 ->
Vue/Ant 映射 -> POC -> 用户验收 -> Context Pack 与支持矩阵开放。

建议优先顺序：

1. `Cascader` / `TreeSelect`：开户行、省市、组织层级。
2. `Drawer`：轻量编辑与详情补充。
3. `Upload` 错误明细、失败文件下载与重新解析。
4. 复杂条件显隐与跨组联动：复杂表单。
5. 树形行、嵌套展开、服务端分页与跨页全选：复杂列表。

通过门槛：新增能力必须有 Schema 校验、至少一个真实 Page Spec、一个可打开预览和
一个自动构建回归样例。禁止只加“提示词说明”。

## 阶段 C：页面族与流程扩展

在详情与结果 POC 经人工验收后，开放它们的快速入口；随后建设更深的业务流程：

| 页面族 | 首个真实验证案例 | 关键能力 |
| --- | --- | --- |
| 详情编辑流 | 分账规则详情 | 从 Detail 转独立 Form、返回定位、未保存提示 |
| 长期处理报告 | 导入结果或四要素处理结果 | 错误行下载、失败重试、处理摘要 |
| 复杂导入 | 批量导入分账规则 | 服务端解析、错误行定位、失败文件下载 |

完成后再将 Feature Spec 流程升级为批量 Vue/Ant 页面构建；在此之前，多页面复杂需求
应先拆为可独立验收的单页 Page Spec。

## 阶段 D：质量与治理

目标是从“可用原型”进入“团队可重复使用”。

- 建立 `qa/fixtures/`：业务 PRD、Page Spec、预期构建结果和人工验收记录。
- 记录组件支持矩阵、Schema 版本、Token 版本和破坏性变更。
- 新能力必须经过产品、UI、前端三个角色的准入检查。
- 资产进入登记库：品牌资产、图标、插图、空状态素材均以语义名引用。
- 构建器保持确定性；MCP 与 OpenDesign 使用同一套工具，不分别实现规则。

建议指标：首次 Page Spec 通过率、一次构建后视觉修改次数、未支持能力出现频率、
能力复用次数和构建阻断原因。

## 阶段 E：推广与平台化

当阶段 D 稳定后：

1. 将 MCP 配置提供给不同 AI 客户端。
2. 将 OpenDesign 快速入口收敛为标准业务入口。
3. 增加 CLI 的版本检查和发布包，避免不同项目复制到不同框架版本。
4. 将框架拆分为平台包：`admin-pc-ant`、未来的 `mobile-h5-vant` 等。

不同端共享业务词汇、资产治理和验收流程，但不共享 Shell、布局密度或组件映射。

## 当前不做

- 不让 AI 直接输出任意 Vue SFC、JS 或 CSS。
- 不为未验证的 Ant 组件预先写大而全模板。
- 不把已验证的父表展开子表延伸为树形表、嵌套展开或与批量选择的组合，直到有独立业务
  样例和验收结论。
- 不将浏览器视觉判断自动化替代用户验收。
- 不在 PC 后台基线稳定前建设移动端、真实后端接口或权限系统。
